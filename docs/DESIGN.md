# 多模态复用实验：设计

状态：草案（框架搭建阶段）。阶段 0 尚未开始。

## 1. 目的

验证：当多模态输入中的一部分不变（图像、视频、系统提示）或到达速率不同时，把"只依赖这部分的计算"提前做并复用，能否在 TTFT 和 E2E 上带来可测的收益。

比较对象是 **M\*** 与 **vLLM-Omni**，两者都在各自的最佳配置下比较，而不是默认配置。

## 2. 基线：两边已经有什么

复用不是从零开始。以下是本仓库 `external/` 中固定版本里的已有机制，实验的收益必须相对这些基线计算。

| 机制 | vLLM-Omni v0.34.0 | M\* 2c8ffde8 |
|---|---|---|
| 编码器输出按内容哈希跨请求复用 | 有：vLLM 的 `EncoderCacheManager`（按 mm hash 共享，容量满时在分配时淘汰）。BAGEL 的 `model_state.py` 还缓存图像布局，缓存命中时不需要像素（`vllm_omni/model_executor/models/bagel/model_state.py:23`） | 未找到。BAGEL 图中 `vit_encoder`、`vae_encoder` 是独立节点（`mstar/model/bagel/bagel_model.py:1259`、`:1282`），但没有按哈希缓存其输出的代码 |
| 前缀 KV 复用 | 有（前缀缓存） | 有（`engine/resources/kv/`）；需确认图像块是否参与哈希 |
| 视频帧到达时预热 | 有：PIL 解码在到达时进行；帧前缀通过 `video-warmup` 请求预先预填（`vllm_omni/entrypoints/openai/video_stream_base.py`，约 470–500 行）。条件：前缀缓存开启且文本输出 | 无对应机制（M\* 的 Qwen3-Omni 视频输入未在本轮检查） |
| 音频增量预填 | 无：有音频输出时关闭增量预填（`_incremental_prefill_active`） | 未检查 |

结论：**vLLM-Omni 已经覆盖了 H1 与 H4 的一部分。** 如果只比较"有/无复用"，会高估 M\* 的收益。M\* 的优势只能在"节点级缓存"这一层体现，而且要证明它在相同配置下有收益。

## 3. 假设

| 编号 | 假设 | 收益来源 |
|---|---|---|
| H1 | 同一图像被多个请求使用时，ViT/VAE 结果复用可省下编码时间 | 编码器时间 |
| H2 | 输入到达时就编码，不等 query 或其他路到齐，可把编码移出 query 关键路径 | query 后的 TTFT |
| H3 | 固定前缀（图像、视频、系统提示）+ 变化的后缀，只重算后缀 | prefill |
| H4 | Qwen3-Omni 视频固定、文本变化时，视觉编码不必重做；视频在文本前时视频 KV 也可复用 | 视觉编码 + 视频 KV |

区分两类收益，分别记录：
- **编码器输出复用**：H1、H4 的视觉部分。不依赖 prompt 顺序。
- **KV 前缀复用**：H3、H4 的视频 KV 部分。依赖 prompt 顺序（视频必须在变化的文本之前）。

## 4. 模型与机器

| 模型 | 用途 | 机器 | 原因 |
|---|---|---|---|
| BAGEL-7B-MoT | H1、H3、阶段 0 画像、H2 近似 | B70（XPU） | 两边都能在 B70 上跑；ViT/VAE 是只依赖图像的独立编码，适合测 H1 |
| Qwen3-Omni | H2 真实多速率流、H4 | 5880（CUDA） | M\* 的 Intel 支持暂不可用；vLLM-Omni 的视频会话机制最完整，需要严格基线 |

BAGEL 的局限：每个请求是一次性提交，没有持续输入。H2 只能用"上传后延迟提交"近似。

注意：BAGEL 生成任务的主要时间在扩散步上，VAE 编码相对很小。img2img 上 VAE 复用的收益可能不大。因此先做阶段 0 画像，再决定是否展开。理解任务（image→text）中 ViT 加图像 token 的 prefill 更重，更可能有收益。

## 5. 流程与闸门

**阶段 0：画像（闸门 1）**
- 在 B70 上对 BAGEL 测 ViT、VAE、LLM prefill、扩散、解码的耗时占比，两边都测。
- 通过条件：编码器（ViT+VAE）占 E2E 的比例足够大，值得继续。若很小，H1 直接记为负面结论，写清上限。

**阶段 1：基线对齐**
- 两边都用各自最佳配置（vLLM-Omni：encoder cache、前缀缓存开启；M\*：KV 前缀缓存开启）。
- 固定随机种子，确认输出一致。

**阶段 2：H1、H3（BAGEL，B70）**
- 场景：同一参考图 + N 个不同 prompt；多图其中一张改变。
- 臂：各自默认最佳 / M\* 新增节点缓存（待实现）。

**阶段 3：H2 近似（BAGEL，B70）**
- 场景：上传图片后延迟 Δ（0、1、3 秒）再提交 prompt。
- 臂：query 时编码 / 上传时编码。

**阶段 4：H2、H4（Qwen3-Omni，5880）**
- 视频 2 fps、音频、文本以各自速率到达；query 随机。
- H4：固定视频 + 变化文本；比较视频在前与文本在前两种顺序。

## 6. 指标与正确性

每个请求记录（格式见 `bench/metrics.py`）：
- TTFT、E2E（query 或提交之后）
- 每个节点或阶段的耗时
- 缓存命中数
- 输出哈希

**正确性检查是必须的**：缓存开启与关闭时，同种子下输出应一致。不一致则该臂结果无效。

重复次数：每个臂至少 3 轮，报告中位数与范围（与 Level 1 实验一致）。

## 7. 需要的代码改动

- **M\***（`external/mstar`）：图 walk 中增加节点输出缓存，键为（节点名、输入内容哈希）；为 H2 增加"输入到达时触发节点"的入口。
- **vLLM-Omni**（`external/vllm-omni`）：大部分已有，主要是配置与测量。若要测音频增量预填，需要放开 `_incremental_prefill_active` 对音频输出的限制。

改动应放在本仓库的补丁文件中（`patches/`），不直接修改 `external/` 的检出内容，保证 `scripts/fetch_externals.sh` 可以重现。（补丁机制待实现。）

## 8. 两台机器的分工

- 同一个 git 仓库，两台机器各自拉取 `external/`（脚本按 `externals.pins` 固定版本）。
- `envs/`、`models/`、`results/` 是本机内容，不进入 git。
- 结果文件按 `results/<实验名>/<机器>/` 存放，报告时合并比较。
- 5880 跑 CUDA（Qwen3-Omni），B70 跑 XPU（BAGEL）。两台机器的框架版本必须一致，由 `externals.pins` 保证。
