  4. **场景 B 有可构造的替代。** 两边的 BAGEL 理解模板都把系统提示放在图像之前（M\* `_render_role_turns`；vLLM-Omni 使用模型目录中的聊天模板），所以"同一图像、不同系统提示"就是图像前的前缀分叉，这正是编码器缓存有独立价值的情形。不再依赖消息内文本与图像的顺序（第 5.2 节）。
  5. **闸门的分母是测试设置造成的。** 审计用 `max_tokens=8` 与 512x512 的纯色图；"ViT 占端到端 16–47%"随输出长度与分辨率变化。R1/R2 的主指标改为 TTFT（首 token）与每请求 GPU 时间；端到端只在固定、写明的输出长度下报告；分辨率作为变量（第 6、8 节）。

## 1. 目的与问题

问题：对于多模态输入中**请求间不变**或**提前可得**的部分，框架能省下多少 GPU 时间与延迟？哪些已经被现有机制拿到，哪些是真正的缺口？

实验要回答：**收益来自哪种机制**；**它的绝对值（毫秒、GPU 秒）与占比**；**在什么负载下出现**（前缀是否在图像之前分叉、分辨率、并发）；以及**是否发生在用户可感知的计时窗口内**。

比较对象是 **M\*** 与 **vLLM-Omni**。归因（哪种机制带来多少）只在同一框架内做；跨框架只比较各自的节省量和现状，不比较绝对端到端。

## 2. 机制分类

| 类别 | 内容 | 精确性 | 节省 | 现状（G0 后） |
|---|---|---|---|---|
| R1 编码器输出复用 | 编码器输出按内容键跨请求复用 | 精确 | GPU 时间、TTFT | vLLM-Omni 有（image→text 与编辑都已观测到跨请求命中）；M\* 无 |
| R1′ 前缀覆盖时跳过编码器 | 图像所在的 KV 已由前缀缓存提供时，不运行编码器 | 精确 | GPU 时间、TTFT | vLLM-Omni 有（调度只看未覆盖的 token 区间）；**M\* 没有：编码器照常运行，输出未被使用** |
| R2 前缀 KV 复用 | 前缀一致时复用 KV | 精确 | GPU 时间、TTFT | 两边都有 |
| R3 非前缀 KV 复用 | 固定段位于可变段之后 | 近似（RoPE 位置） | GPU 时间 | 不在本次范围 |
| L1 到达即计算 | 输入未全到就做能做的部分 | 精确，不省算力 | query 之后的关键路径 | vLLM-Omni 视频会话（文本输出时）；M\* 无 |

三者的关系（同一图像重复出现时）：

| 图像之前的前缀 | 前缀覆盖图像 | 需要编码器输出吗 | vLLM-Omni | M\* |
|---|---|---|---|---|
| 一致 | 完全覆盖 | 不需要 | 不跑 ViT（R1′） | **仍跑 ViT（浪费）** |
| 一致 | 部分覆盖（命中停在图像内） | 需要 | 编码器缓存命中（R1） | 跑 ViT |
| 分叉（不同系统提示/历史） | 不覆盖 | 需要 | 编码器缓存命中（R1） | 跑 ViT |

## 6. 计时口径

- **主指标（R1、R1′、R2）**：TTFT（流式，首个文本 token），与每请求 GPU 时间（服务端各节点同步耗时之和）。

## 8. 阶段 0：画像与闸门

### 8.1 方法

- 每个任务、每档分辨率测各节点耗时：ViT、VAE encode、LLM prefill、decode/扩散、VAE decode。
- 关闭会改变工作量的缓存，用计数器核对命中为 0。
- warmup：每个（任务、分辨率）组合至少 3 次，丢弃。审计中 vLLM-Omni 的第一个图像请求 837 ms，第二个新图 247 ms，说明需要按路径 warmup。
- 节点耗时取法：
  - M\*：`mstar_step_seconds_sum / _count`；先确认它是否带设备同步。
  - vLLM-Omni：shim 对 `_encode_vit` 计时（带同步）；LLM 部分用阶段耗时日志与 `vllm:` 直方图。
  - XPU：同步改用 `torch.xpu.synchronize`。
- 计时 shim 本身会插入同步，**只用于画像轮**；TTFT 与吞吐轮关闭计时，只保留计数（第 13 节）。

### 8.2 闸门

```
上界 = 每请求可省的编码器时间（或 LLM prefill 时间） × 可复用比例 − 查找与哈希开销
```

- 判断对象是 **TTFT 与每请求 GPU 时间**，不是 `max_tokens=8` 的端到端。
- **通过条件（已定，2026-11-25，测量前写定）**：任一成立即通过——
  - 延迟：`上界 / TTFT ≥ 5%` **且** `上界 ≥ 10 ms`；
  - 吞吐：`上界 / 每请求 GPU 时间 ≥ 5%`。
- 取值理由：5% 是同框架重复测量能稳定分辨的量级（G0 中热请求的 TTFT 抖动在几毫秒到十几毫秒，需由 G1 的噪声底确认；若噪声底的四分位距超过 TTFT 的 5%，则以"超出噪声底 2 倍"代替 5%）；10 ms 排除"比例大但绝对值可忽略"的短请求情形；吞吐口径单独成立，因为编码器节省的 GPU 时间在并发下才转化为收益（5.3）。
- 每个（任务、分辨率、序列）分别判断；结论写入结果目录，不因后续数据改阈值。
- M\* 的 I1（跳过被覆盖的编码器）几乎没有实现成本、没有显存成本，闸门只要求"S1 或 S4 中被浪费的 ViT 时间 ≥ 10 ms"。

## 9. M\* 的改进与原型（闸门通过后）

- **I1：前缀覆盖时跳过编码器。** 在调度编码器 walk 之前查询 LLM 的前缀覆盖；被完全覆盖的图像 span 不运行 `vit_encoder`（编辑任务同理处理 `vae_encoder`）。需要确认：被跳过后，同一请求是否还有别的 walk 读取该编码器输出（例如 CFG 分支）。
- **I2：编码器输出缓存。** 键覆盖：节点、解码后的像素内容与预处理几何（"a file's digest doesn't cover the resize"，`bagel_model.py:905–906`）、模型与处理器版本、dtype。粒度为每张图像；容量按字节上限与 LRU；报告淘汰与查找开销。
- 先做 I1，再按 S2 的结果决定 I2。

## 16. 主场景（v7）：摄像头流 + 随时提问（Qwen3-Omni，文本输出起步）

### 16.1 场景与为什么选它

家庭/机器人助手：摄像头以 1–2 fps 持续送帧（每帧一个 image 项，640x480 → 300 token），用户在任意时刻提问（先文本，后语音）。指标是**提问到首 token**，以及每个会话的**总 GPU 工作量**（编码器调用次数与耗时、prefill token 数）。

它同时含有三类可提前或可复用的部分：

| 部分 | 到达/变化方式 | 可做的事 | 精确性 |
|---|---|---|---|
| 系统提示（与固定参考图） | 跨会话不变 | 前缀 KV 复用（R2）、编码器输出复用（R1） | 精确 |
| 帧 | 持续到达、早于提问 | 到达即编码 + 增量 prefill（L1） | 精确：image 项追加不改变此前 token 的位置（CPU 已在三种实现上核对，`agents_results/2026-11-26_tmrope-image-items-prefix-invariance.md`） |
| 帧缓冲滑动（丢弃最旧帧） | 前缀改变 | KV 前缀失效，只剩编码器输出可复用 | 精确（编码器输出与位置无关） |
| 提问（文本/语音） | 最后到达 | 只能在到达后算 | — |

视频（video 项）不用于本场景：两边的时间步都依赖整段时长（M\* `spg = 2/sample_fps`），增量 prefill 不精确（`agents_results/2026-11-26_mstar-qwen3-incremental-exactness.md`）。

### 16.2 两个框架的现状（源码审计，未上 GPU）

| | vLLM-Omni v0.34.0 | M\* 2c8ffde8 |
|---|---|---|
| 流式入口 | `WS /v1/video/chat/stream`：每帧一个 image 项（uuid = md5(bytes)） | Qwen3-Omni 没有（`/v1/realtime` 拒绝；无视频流） |
| 到达即算（帧） | 有：每当缓冲变化且空闲时发一个 `max_tokens=1` 的 warmup 请求（串行、合并），KV 进全局前缀缓存；**仅文本输出**（`video_stream_base.py:297-299` 的范围限制，PR #5894 无技术理由） | 无；可用同样的客户端 warmup 模拟（图像项按文件摘要入前缀键，`qwen3_omni_model.py` 的 `kv_labels`） |
| 前缀覆盖的帧是否重跑编码器 | 不跑（调度只看未计算的 token） | **重跑**：视觉节点总在 Thinker 查前缀之前运行；每次 warmup/提问都把缓冲里的全部帧再编码一遍 |
| 编码器输出缓存 | 有（62720 embedding，640x480 可放 209 帧；未在日志确认） | 无 |
| 缓冲满时 | 丢弃最旧的一半（`:663`），前缀失效，靠编码器缓存 | 由客户端决定 |
| 语音提问 | 音频只缓冲，提问时才编码 | 同（一次请求） |

smoke 证实（`results/smoke/5880/mstar/q3-stream/NOTES.md`）：M\* 每次 warmup 与提问都重编码缓冲中的全部帧（30 帧 946 ms），编码器工作量随会话长度二次增长；这是 BAGEL 上"前缀命中仍跑 ViT"（第 2 节）的放大版。另一个结构性差别：M\* 把每张图像拆成独立的一对 walk（视觉编码 → Thinker prefill），串行执行，Q 臂的 Thinker prefill 每张约 91 ms。

### 16.3 臂

同一框架内对照；两边用同一个客户端（`bench/stream.py`）与同一帧序列。

| 臂 | 含义 | vLLM-Omni | M\* |
|---|---|---|---|
| Q | 只在提问时发请求（含全部缓冲帧） | 聊天接口 | 聊天接口 |
| W | 客户端 warmup：缓冲变化且空闲时发 `max_tokens=1` 的前缀请求（与 vLLM-Omni 的 WS 逻辑相同：串行、合并、提问时取消） | 聊天接口 | 聊天接口 |
| W-native | vLLM-Omni 自带 WS 端点 | 是 | — |
| W+I | W + M\* 改动：被前缀覆盖的帧不重跑编码器（I1），或编码器输出缓存（I2） | — | 改源码 |

负载：
- **L-grow**：缓冲只增不减（≤ 50 帧），提问间隔 10–30 s；前缀一直有效。
- **L-slide**：缓冲满后丢最旧的一半（与 vLLM-Omni 相同）；丢弃后前缀失效，检验编码器输出复用。
- **L-fixed**：每个会话以同一系统提示 + 固定参考图开头，多个会话先后进行；检验跨会话复用。

### 16.4 计时与记录

- 两种运行模式：**timing**（真实节奏，帧不断、warmup 不等计数器；只报告 TTFT 与端到端，以及整段会话的计数器差）与 **audit**（提问前暂停送帧并等计数器稳定，提问后再等，得到单个提问的前缀命中与编码器调用）。
- 每帧记录发送时刻；每个 warmup 记录开始、结束、是否被取消、包含的帧数；每个提问记录 `t_query`、`t_first_out`、`t_done`、提问时是否有 warmup 在途、提问时缓冲帧数与已 warmup 的帧数。
- 会话级：编码器调用次数与耗时之和（M\*：`mstar_step_seconds{component="vision_encoder"}`；vLLM-Omni：shim 计数）、prefill 命中与查询 token。

## 18. 图调度是否天然更适合做这类优化（2026-11-28）

|---|---|---|---|---|
| M1 编码器输出缓存 | M\* | 约 150 行；同一组件用于 Qwen3-Omni 视觉与 BAGEL ViT，各加约 30 行 | W 臂提问编码 0 帧；每会话编码器 GPU 时间 −86%；BAGEL 重复提问 −20~33% | 有（mm_hash 编码器缓存 + 只为未计算 token 调度编码器） |

改动之后（G3 M4 轮）：Q 臂 M\* 与 vLLM-Omni 持平（首次满窗快 13%），W 臂 M\* 0.17–0.28 s 对 vLLM-Omni 0.10–0.15 s。BAGEL 512 持平，980 差 35 ms。

### 18.2 图调度确实让什么变容易了

1. **按节点插入复用**：M1 只碰视觉节点与引擎的"缓存服务的行"一处，其他节点不知道它的存在；同一组件换个模型（BAGEL ViT）只需 30 行。vLLM 的同类能力在调度器与 model runner 里，是框架级功能，模型作者不能按自己的需要改。
2. **粒度是模型的选择**：M3/M4 把"几张图一个子图"变成模型文件里的一个参数，引擎不改。vLLM-Omni 里同样的事（编码器批大小、prefill 怎么合并）由调度器的预算决定，模型无法表达"这几项永远一起处理"。
3. **放置是配置**：编码器放在哪张卡是 `node_groups` 的一行（E2 检验其价值）。vLLM-Omni 的编码器在 Thinker 的 model runner 里，与 decode 同一步、同一卡。

### 18.3 图调度让什么变难了（测量到的代价）

1. **每个 walk 的固定开销**：一个 walk 一次往返约 12 ms，即使整段被缓存跳过；同一请求的 walk 严格依次执行，后一张图的编码要等前一张图的 Thinker prefill（真实依赖只有"编码 → 同一张图的 prefill"与"prefill 按顺序"）。48 帧 48 个 walk 时这是主要开销。
2. **跨节点的知识没有被用上**：前缀缓存的判断在 Thinker 节点，上游视觉节点不知道自己的输出会被丢掉，于是前缀命中仍跑 ViT（G1、G3 基线），输出照样传给 TP rank 1（48 帧 225 MB）。图里有依赖信息（视觉节点的唯一消费者是同一 walk 的 Thinker），但运行时不用它来剪枝。
3. **变粗受限于上游限制**：分组超过 Thinker 每步预算（1024）时被分块，分块 + 前缀缓存 + TP2 出错；视觉编码的显存规划只按单次调用上限，48 张一次调用 OOM。
4. **数据面**：每个请求重发并重新处理全部帧（M4 之前每请求写 531 MB 共享内存）。这一项是实现缺失，不是图的形式造成的。

### 18.4 结论与候选改动

结论：图的形式让"复用/提前算"**容易表达、容易局部实现**（每项改动都在 150 行内、不动其他节点），但 M\* 当前的运行时**没有利用图里的依赖信息**（剪枝、提前、并行），反而为细粒度付出每个 walk 的固定开销。vLLM-Omni 的集中式调度器把最常见的几种复用（编码器缓存、前缀覆盖跳过编码器、处理器缓存）做成了内置功能，开箱即用，但新的模式（音频会话 warmup、只编码不 prefill）要改端点或调度器。到目前为止，M\* 的改动都是在**追平** vLLM-Omni 已有的能力；图调度可能**超过**它的地方在下面 C1–C5，尚未实现：

| 编号 | 改动 | 为什么是图调度特有的 | 预期收益（依据） | 难度 |
|---|---|---|---|---|
| C1 | 按依赖剪枝：前缀租约已覆盖的图不编码、不传 | 图知道视觉节点的唯一消费者 | **已实现（18.6）**：48 帧全缓存进入调度→首 token 162–179 → 120–145 ms，卡间传输 400 → 5 MB；G3 W 臂 TTFT 166–280 → 158–231 ms。整段 walk 仍要调度（每个约 17 ms） | 中 |
| C2 | 编码 walk 提前、与 Thinker prefill 并行 | 真实依赖只有"编码 → 本图 prefill"；多声明一个分区即可并发 | **已实现（18.6）**：48 帧冷请求 2.64 s（C1，rank 0）→ 1.90 s；G3 Q 臂第一个满窗 2023 → 1697 ms（vLLM-Omni 2336） | 中：没改引擎与调度器 |
| C3 | 编码器独占一卡（配置） | 节点放置是配置 | **已验证（E2）**：3 会话时每 token 25.3 → 11.3 ms | 低：只改配置 |
| C4 | 长会话请求：帧作为客户端流追加到同一个请求（M\* 已有 client stream 机制，用于全双工语音与 Waypoint） | 一个请求的子图可以随输入增长 | **已实现轻量版（18.7）**：不改请求模型，已送达的帧发引用、客户端提示已预热的帧数，这些帧并成一个 walk 由 C1 跳过。G3 W 臂 TTFT 156–237 → 112–130 ms，不再随帧数增长，7 个提问点中 6 个快于 vLLM-Omni（105–152）；请求体 4.8 MB → 7 KB。完整版（流式追加）未做 | 轻量版中：补丁 07 共 136 行改动（模型 107、编码器 12、data worker 17），客户端约 40 行。完整版高：Qwen3-Omni 要声明帧流与提问流、循环结构；滑动窗口要从 KV 头部删除，需重设位置 |
| C5 | 只编码不 prefill 的到达即算（滑动窗口、提问时才决定取哪些帧） | 可以只提交编码器子图 | 前缀不稳定时省去 warmup 的 prefill（vLLM-Omni 的 warmup 总是 prefill） | 中 |

语音提问（M2/V2）：测得收益上限 5–120 ms（`v1-audio/NOTES.md`），暂不做。

### 18.5 E2：多会话与编码器放置

脚本 `scripts/run_e2_multi_cuda.sh`，客户端 `bench/stream_multi.py`：3 个摄像头会话同时运行（开始时间错开 2.7 s），W 臂，grow，2 fps，回答 64 token（"Describe the most recent image in two sentences…"）；先 1 个会话作无干扰参照。记录每个提问的 TTFT 与逐 token 间隔。
变体：vLLM-Omni（2 卡）；M\*（M1+M3(16)+M3b+M4，大步预算，3 卡）编码器在 rank 0（与 Thinker 同卡，`..._bigstep.yaml`）或 rank 2（`..._bigstep_enc2.yaml`）。
结果（`results/e2-multi/5880/NOTES.md`）：3 个会话同时运行时，M\* 回答的每 token 时间编码器同卡 25.3 ms、独占一卡 11.3 ms（单会话 6.5 ms），vLLM-Omni 13.3 ms（单会话 8.6 ms）。编码器放置只改一行配置，输出逐字相同。TTFT 上 M\* 仍是 vLLM-Omni 的 2–3 倍（287–315 对 108 ms）：提问排在别的会话的 warmup prefill 后面，且每请求重发全部帧——这正是 C1、C4 针对的部分。
这是目前唯一一项 M\* 靠图调度的特性（节点放置）**超过**而不只是追平 vLLM-Omni 的结果；C3 已验证。

### 18.6 C1 与 C2 的实现与结果

C1（`MSTAR_C1=1`，`results/smoke/5880/mstar/c1-profile/NOTES.md`）：提示开头文本单独成一步，Thinker rank 0 在任何编码之前取到前缀租约，并登记"前多少张图整个落在租约里"（原型用 /dev/shm 文件，正式做法应随步报告交给调度器）；调度器对整组被覆盖的步不发像素，编码器只编码没覆盖的图，Thinker 按网格补零，引擎检查补零区都在命中范围内。输出逐字相同。效果见 18.4 表。剩余开销是 walk 本身：什么都不算、不传的 walk 仍约 17 ms；整段跳过要改 Thinker 的 KV 游标与位置推进，不是局部改动。

C2（`MSTAR_C2=1`，`results/smoke/5880/mstar/c2-profile/NOTES.md`）：多一个 `VisionAhead` 分区和第二个 ViT 节点（与主编码器同进程、共享 M1 缓存），请求进入即依次编码各组，Thinker 的图像 walk 到时命中缓存。输出逐字相同。同一放置（rank 2）下 48 帧冷请求 3.17 → 2.68 s，编码只剩第 0 组在关键路径上。没改引擎与调度器。

对本节问题的更新：C1 要改引擎/KV 管理器/调度器各一处（依赖信息原本不在调度层），C2 只在模型里多声明一个分区——后者是"图的形式天然适合"的直接证据。两者都让 M\* 前进了一步，但 W 臂 TTFT 仍是 vLLM-Omni 的约 1.5 倍（每个 walk 的固定开销），冷请求受 rank 2 放置下 Thinker 变慢所限。

rank 2 放置下 Thinker prefill 慢约 50% 的原因（`results/smoke/5880/mstar/placement-profile/NOTES.md`）：显存够时 M\* 捕获了 4096–16384 token 的 prefill 图，16 张一组（约 4900 token）补齐到 8192 回放，比 eager 慢约 40%；rank 0 放置时这些图因显存不足捕获失败，反而走 eager。rank 2 的配置加 `prefill_token_buckets`（图像 prefill 只捕获到 2048）后，三种放置的 Thinker prefill 相同（约 1.02 s），C2 的 48 帧冷请求 1.90 s（rank 0 的 C1 为 2.64 s，−28%）。G3 不预热的提问：M\* 7 个提问点中 6 个快于 vLLM-Omni，第一个满窗 1697 对 2336 ms。

### 18.7 C4 轻量版的实现与结果

C4（`MSTAR_C4=1`，`results/smoke/5880/mstar/c4-profile/NOTES.md`，G3 结果 `results/g3-stream/5880/NOTES.md` 的 C4 轮）：不改请求模型，仍是一问一个请求。
- 服务端第一次加载某帧时把字节存到 `/dev/shm/mstar_c4_frames/<xxh3-128>`；客户端之后只发引用（data URL 内容为 `MSTAR-FRAME:<xxh3-128>`）。data worker 把引用按原帧算前缀键，所以一帧整帧发送与作为引用发送共用同一批 KV 页。
- 请求顶层字段 `c4_warm = n`：前 n 张图整段在本会话较早的请求里。模型把这 n 张图并成一个图像步（不受 16 张一组的限制），C1 整组跳过，像素不发。租约实际不覆盖时编码器报错，客户端整帧重发一次。提示 = 与上一个成功请求的公共帧前缀 − 1（那个请求的最后一帧可能止于半页）。
- 正确性：8 个提问整帧与引用 + 提示两种发法与参照逐字相同；G3 的 688 个请求没有一次重发。

结果：W 臂的提问 TTFT 从"每 16 帧一个 walk"变成"已预热的帧一个 walk + 新帧与问题一个 walk"，48 帧时 232 → 120 ms，16–48 帧都在 112–130 ms。这是 W 臂第一次在多数提问点快于 vLLM-Omni。
对本节问题的更新：这一步的收益来自"按会话知识改变子图的粒度"（已预热的部分合成一个 walk），而 walk 的粒度是模型的选择（18.2 第 2 点）；vLLM-Omni 没有对应的旋钮，但它也不需要——它的调度器没有每个 walk 的固定开销。所以 C4 轻量版更准确地说是**抵消**了图调度的固定开销，而不是图调度独有的收益。真正图调度独有的是 C2（多声明一个分区即可并发）与 C3（放置是配置）。
