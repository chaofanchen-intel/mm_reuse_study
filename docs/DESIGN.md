## 0. 修订记录

- v1–v3：从"复用有收益"的假设出发，逐步拆分机制、加入闸门、双重计时与按任务画像。
- v4：按 G0 审计更正 vLLM-Omni 的结论（image→text 必须带 `modalities: ["text"]`）；BAGEL 以 image→text 为主任务。
- **v6（本版）**：负责人确认 v5 的全部方向；闸门阈值定为第 8.2 节的值；Qwen3-Omni 提前，与 G1 并行（第 11 节）；第 13 节的结构已实现。
- **v5 对 v4 的修正：**
  1. **M\* 的缺口定位错了。** M\* 在前缀命中时仍运行 `vit_encoder`，但 LLM 的 `prefill_vit` walk 被前缀缓存跳过，ViT 的输出没有被使用。vLLM-Omni 的调度器只为未被已缓存 token 覆盖的图像调度编码器。所以 M\* 的第一项改进是"前缀覆盖时跳过编码器"（I1，不占显存、精确），编码器缓存（I2）只在前缀在图像之前就分叉时才有额外收益。v4 只写了 I2（第 2、5.1 节）。
  2. **2×2 对照的两个开关不独立。** 在 vLLM-Omni 中，前缀命中完全覆盖图像时编码器根本不被调度，臂 2 与臂 3 相同；部分覆盖（块对齐导致命中停在图像内部，审计中 1344 < 图像末尾）时才需要编码器输出。对照要记录"图像被前缀覆盖的程度"，不能只记开关（第 5.1 节）。
  3. **M\* 的 image→text 审计证据被重复请求污染。** `results/g0/5880/mstar/i2t-settled-repeats/` 的每个请求都与同一服务上更早一轮的请求完全相同，所以命中 1408/1409（连问题文本都命中）。它不能说明"同图不同问题"或"文本在前"的行为；v4 第 3.1 节与第 5.2 节据此得出的结论作废。"新图命中 0"的证据只在仓库外的临时脚本输出中。需要在新服务上重测（第 3.4 节）。
  4. **场景 B 有可构造的替代。** 两边的 BAGEL 理解模板都把系统提示放在图像之前（M\* `_render_role_turns`；vLLM-Omni 使用模型目录中的聊天模板），所以"同一图像、不同系统提示"就是图像前的前缀分叉，这正是编码器缓存有独立价值的情形。不再依赖消息内文本与图像的顺序（第 5.2 节）。
  5. **闸门的分母是测试设置造成的。** 审计用 `max_tokens=8` 与 512x512 的纯色图；"ViT 占端到端 16–47%"随输出长度与分辨率变化。R1/R2 的主指标改为 TTFT（首 token）与每请求 GPU 时间；端到端只在固定、写明的输出长度下报告；分辨率作为变量（第 6、8 节）。
  6. **缺少吞吐口径。** 并发 1 时，R1 的延迟收益最多是一次 ViT（几十毫秒）；它节省的 GPU 时间在并发下才转化为吞吐。增加每请求 GPU 时间与一个小规模并发实验（第 5.3 节）。
  7. **跨框架的 prompt 不一致。** 两边的默认系统提示不同（M\*："You are BAGEL…"；vLLM-Omni 的聊天模板默认 "You are Qwen…"，待日志确认），图像 token 数也不同（查询 1409 vs 1383）。跨框架只比较各自框架内的节省量；两边都显式传同一系统提示（第 12 节）。
  8. **架构问题**：没有统一的客户端与结果格式、服务启动靠手工命令、测量 shim 影响计时、文档与代码不一致。见第 13 节。

## 1. 目的与问题

问题：对于多模态输入中**请求间不变**或**提前可得**的部分，框架能省下多少 GPU 时间与延迟？哪些已经被现有机制拿到，哪些是真正的缺口？

实验要回答：**收益来自哪种机制**；**它的绝对值（毫秒、GPU 秒）与占比**；**在什么负载下出现**（前缀是否在图像之前分叉、分辨率、并发）；以及**是否发生在用户可感知的计时窗口内**。

比较对象是 **M\*** 与 **vLLM-Omni**。归因（哪种机制带来多少）只在同一框架内做；跨框架只比较各自的节省量和现状，不比较绝对端到端。

## 2. 机制分类

| 类别 | 内容 | 精确性 | 节省 | 现状（G0 后） |
|---|---|---|---|---|
| R1 编码器输出复用 | 编码器输出按内容键跨请求复用 | 精确 | GPU 时间、TTFT | vLLM-Omni 有（image→text 与编辑都已观测到跨请求命中）；M\* 无 |
| R1′ 前缀覆盖时跳过编码器 | 图像所在的 KV 已由前缀缓存提供时，不运行编码器 | 精确 | GPU 时间、TTFT | vLLM-Omni 有（调度只看未覆盖的 token 区间）；**M\* 没有：编码器照常运行，输出未被使用** |
| R2 前缀 KV 复用 | 前缀一致时复用 KV | 精确 | GPU 时间、TTFT | 两边都有 |
| R3 非前缀 KV 复用 | 固定段位于可变段之后 | 近似（RoPE 位置） | GPU 时间 | 不在本次范围 |
| L1 到达即计算 | 输入未全到就做能做的部分 | 精确，不省算力 | query 之后的关键路径 | vLLM-Omni 视频会话（文本输出时）；M\* 无 |

三者的关系（同一图像重复出现时）：

| 图像之前的前缀 | 前缀覆盖图像 | 需要编码器输出吗 | vLLM-Omni | M\* |
|---|---|---|---|---|
| 一致 | 完全覆盖 | 不需要 | 不跑 ViT（R1′） | **仍跑 ViT（浪费）** |
| 一致 | 部分覆盖（命中停在图像内） | 需要 | 编码器缓存命中（R1） | 跑 ViT |
| 分叉（不同系统提示/历史） | 不覆盖 | 需要 | 编码器缓存命中（R1） | 跑 ViT |

## 5. 实验设计

### 5.1 BAGEL image→text：请求序列与对照

**请求序列（每个序列在新启动的服务上运行）**：

| 序列 | 内容 | 期望在 vLLM-Omni 上 | 要回答的问题 |

| S4 多轮对话 | 第 1 轮图 A + 问题；后续轮带历史 | 完全覆盖 | R1′ 与 R2 |

**对照（同一框架内）**：

| 干预 | vLLM-Omni 如何关闭 | M\* 如何得到 |
|---|---|---|
| R2 前缀缓存 | 部署配置 `enable_prefix_caching: false` | 请求级 `prefix_cache: false` |

## 6. 计时口径

- **主指标（R1、R1′、R2）**：TTFT（流式，首个文本 token），与每请求 GPU 时间（服务端各节点同步耗时之和）。

## 8. 阶段 0：画像与闸门

### 8.1 方法

- 每个任务、每档分辨率测各节点耗时：ViT、VAE encode、LLM prefill、decode/扩散、VAE decode。
- 关闭会改变工作量的缓存，用计数器核对命中为 0。
- warmup：每个（任务、分辨率）组合至少 3 次，丢弃。审计中 vLLM-Omni 的第一个图像请求 837 ms，第二个新图 247 ms，说明需要按路径 warmup。
- 节点耗时取法：
  - M\*：`mstar_step_seconds_sum / _count`；先确认它是否带设备同步。
  - vLLM-Omni：shim 对 `_encode_vit` 计时（带同步）；LLM 部分用阶段耗时日志与 `vllm:` 直方图。
  - XPU：同步改用 `torch.xpu.synchronize`。
- 计时 shim 本身会插入同步，**只用于画像轮**；TTFT 与吞吐轮关闭计时，只保留计数（第 13 节）。

### 8.2 闸门

```
上界 = 每请求可省的编码器时间（或 LLM prefill 时间） × 可复用比例 − 查找与哈希开销
```

- 判断对象是 **TTFT 与每请求 GPU 时间**，不是 `max_tokens=8` 的端到端。
- **通过条件（已定，2026-11-25，测量前写定）**：任一成立即通过——
  - 延迟：`上界 / TTFT ≥ 5%` **且** `上界 ≥ 10 ms`；
  - 吞吐：`上界 / 每请求 GPU 时间 ≥ 5%`。
- 取值理由：5% 是同框架重复测量能稳定分辨的量级（G0 中热请求的 TTFT 抖动在几毫秒到十几毫秒，需由 G1 的噪声底确认；若噪声底的四分位距超过 TTFT 的 5%，则以"超出噪声底 2 倍"代替 5%）；10 ms 排除"比例大但绝对值可忽略"的短请求情形；吞吐口径单独成立，因为编码器节省的 GPU 时间在并发下才转化为收益（5.3）。
- 每个（任务、分辨率、序列）分别判断；结论写入结果目录，不因后续数据改阈值。
- M\* 的 I1（跳过被覆盖的编码器）几乎没有实现成本、没有显存成本，闸门只要求"S1 或 S4 中被浪费的 ViT 时间 ≥ 10 ms"。

## 9. M\* 的改进与原型（闸门通过后）

- **I1：前缀覆盖时跳过编码器。** 在调度编码器 walk 之前查询 LLM 的前缀覆盖；被完全覆盖的图像 span 不运行 `vit_encoder`（编辑任务同理处理 `vae_encoder`）。需要确认：被跳过后，同一请求是否还有别的 walk 读取该编码器输出（例如 CFG 分支）。
- **I2：编码器输出缓存。** 键覆盖：节点、解码后的像素内容与预处理几何（"a file's digest doesn't cover the resize"，`bagel_model.py:905–906`）、模型与处理器版本、dtype。粒度为每张图像；容量按字节上限与 LRU；报告淘汰与查找开销。
- 先做 I1，再按 S2 的结果决定 I2。

## 13. 代码架构

### 13.1 v5 时的问题（v6 已处理）

| 问题 | 后果 |
|---|---|
| 两个审计脚本各写一套请求与解析，输出格式不同，`bench/g0_audit_vllm_omni.py` 从 `bench/g0_audit_mstar.py` 导入函数 | 两边结果不能直接合并；`RequestRecord` 没有被任何脚本使用 |
| 请求不是流式的 | 测不到 TTFT，只有端到端 |
| 服务靠手工命令启动（GPU 放置、环境变量、shim、模型名） | 本轮出现过重复启动、残留进程导致 OOM、放错卡；启动参数没有随结果保存 |
| vLLM-Omni 的模型名是快照路径 | 客户端硬编码路径 |
| shim 的计时插入设备同步，且总是开启 | 影响 TTFT 与吞吐的测量 |
| 结果目录没有机器层级（当时为 `results/g0/mstar-settled` 等） | 与第 14 节的约定不一致，B70 的结果会混在一起 |
| `README.md` 写的机器分工（5880 做 Qwen3-Omni、B70 做 BAGEL）、`bench/plan.py` 的臂与场景、`bench/metrics.py` 的版本说明都已过时 | 文档与代码互相矛盾 |

### 13.2 结构（v6 已实现）

```
bench/
  client.py           # 统一的 OpenAI 兼容流式客户端：时间线、TTFT、输出长度
  adapters/
    mstar.py          # /metrics → 规范化计数（encoder_ran、prefix_hit_tokens、节点耗时）
    vllm_omni.py      # /metrics + shim 日志 → 同样的规范化计数
  sequences.py        # S1–S4 的请求序列；图像在代码中确定性生成（主色 + 按 id 播种的噪声）
  summarize.py        # 按 框架 × 臂 × 序列 × 分辨率 × 观测状态 汇总（中位数、IQR、正确率）
  runner.py           # 序列 × 臂 → RequestRecord JSONL，检查服务是否为新启动
  metrics.py          # RequestRecord（第 10.1 节字段）
  plan.py             # 实验矩阵
  audit/g0_bagel_gen.py  # t2i 与编辑的 G0 审计（调用 client 与 adapters）
  audit/legacy/          # 旧审计脚本，只作 results/g0/5880 早期结果的出处
scripts/
  serve_mstar_cuda.sh       # 启动服务；写入启动清单与 PID 文件；拒绝在已占用的卡或端口上启动
  serve_vllm_omni_cuda.sh   # 同上；固定 --served-model-name bagel；shim 模式 off/count/time
  stop_serve.sh             # 按 PID 文件停止本仓库启动的服务
  audit_vo/sitecustomize.py # 测量 shim：VO_AUDIT_MODE=count|time
tests/test_tooling.py        # 离线测试：序列、渲染、适配器覆盖判定、runner 端到端（假服务）
results/<实验名>/<机器>/<框架>/
```

### 13.3 迁移状态

1. `serve_*.sh` 与 `stop_serve.sh`：完成。启动前检查同名服务、端口、GPU 显存（超过 1000 MiB 拒绝）；以新会话启动，停止时结束整个进程组；启动清单含命令、配置哈希、GPU、框架 commit 与是否有改动、shim 模式。已用假进程自测。
2. `client.py`（流式，TTFT 与 usage）与两个 adapter：完成。覆盖程度按观测判定（M\*：LLM 消费图像的 walk 是否运行；vLLM-Omni：编码器是否被调度），见各适配器的文档字符串。
3. `runner.py`、`sequences.py`、`summarize.py`、`audit/g0_bagel_gen.py`：完成，离线测试通过。用它完成 3.4 的 M\* 重测与两边的 S1–S4：**待 GPU**。
4. 结果目录迁移到 `results/<实验>/5880/<框架>/`：完成（`results/g0/5880/`、`results/smoke/5880/`）。

运行约定：
- 机器名来自 `MM_MACHINE`（`scripts/env_cuda.sh` 默认 5880，`scripts/env_xpu.sh` 默认 B70）。
- 每个臂一个服务目录：`results/<实验>/<机器>/<框架>/<臂>/server/`；记录写在同级 `records.jsonl`。
- vLLM-Omni 的测量轮用 `--shim count`；画像轮用 `--shim time`。
- M\* 的 image→text 用 `configs/bagel_mstar_i2t.yaml`（上游单卡配置 + `gpu_memory_fraction: 0.85`）；两个前缀臂在同一服务上用请求级开关，图像 id 含臂名，互不命中。
- vLLM-Omni 的两个前缀臂需要两个服务（`configs/bagel_vllm_omni_audit.yaml` 与 `_noprefix.yaml`）。
- XPU 版的 serve 脚本未写（B70 上按同样接口补 `serve_*_xpu.sh`）。
